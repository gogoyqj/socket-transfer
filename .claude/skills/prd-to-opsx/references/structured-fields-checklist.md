# 结构化字段强制确认清单

阶段二歧义质量过滤时使用。

---

## ⚡ 通用兜底规则（优先级高于以下十种类型）

**凡是会写入 `design.md` 的结构化实体，无论是否命中以下十种类型，其字段定义（名称、类型、约束、枚举值）若无法从 PRD 原文引用，均视为「PRD未说明」，强制标注 `[需确认]`，进入阶段三向用户确认。**

适用范围：DB 表、缓存结构、API 请求/响应、MQ 消息体、配置字段、枚举映射、文件格式、Webhook payload——以及任何其他将被写入 design.md 的结构化定义，即使不属于以下十种类型中的任何一种。

**判断标准：「推导出合理值」≠「PRD 已说明」**

- ✅ **PRD 已说明**：可以引用 PRD 中的原句（例如："PRD 第3节写明字段类型为 VARCHAR(255)"）
- ❌ **PRD 未说明**：只能说"根据业务语义可推断"、"通常这类字段用 TINYINT"、"合理的设计应该是……"

无论推导结果多么合理，只要无法引用 PRD 原文，该条目一律视为未说明，强制标注 `[需确认]`。禁止走以下隐性路径：PRD 未说明 → AI 推导出合理值 → 视为「已说明」→ 跳过确认。

> 以下十种类型是详细操作指南，告诉你每类需确认哪些子项，但不限定全部范围。

---

## 类型一：对外提供的接口（我方暴露的 API / RPC / WebSocket）

PRD 通常只描述功能，省略字段级细节。

**需确认的内容**：
- 鉴权方式：Bearer Token / API Key / Session Cookie / 无鉴权
- 每个请求字段：字段名、类型（string/int64/bool...）、是否必填、约束（长度/格式/取值范围）
- 每个响应字段：字段名、类型、空值语义（null / 空数组 / 省略字段 三者含义不同）
- 分页参数规范（若有列表接口）：cursor 还是 offset、页大小上限
- 排序参数规范（若有排序）：字段名及方向的传参格式
- 错误码列表及含义
- WebSocket 消息：event type 枚举、每种 event 的 payload 结构

---

## 类型二：第三方依赖接口（调用外部服务）

**此类条目必然标注 `[需确认]`，无需逐项判断**——接口结构、鉴权、错误码均无法从 PRD 或代码库推断。

**需确认的内容**：
- 请求结构：endpoint、method、header、body 字段及类型
- 响应结构：成功和失败的字段及含义
- 鉴权方式：API Key / OAuth 2.0 / HMAC 签名 / IP 白名单
- 错误码列表及含义
- 回调 / webhook 格式与验签方式（如有）
- 限流规则：QPS 上限、频率限制
- 重试策略：幂等性保证、最大重试次数
- 沙箱与生产环境的差异（域名、密钥、行为）
- 调用失败时的降级 / 兜底策略

---

## 类型三：数据库表字段

PRD 通常只描述业务实体，不涉及存储细节。

**需确认的内容**：
- 每个字段：字段名、数据库类型（VARCHAR(n)/BIGINT/TINYINT...）、是否非空、默认值
- 索引策略：哪些字段需要索引、是否唯一索引、联合索引字段顺序
- 枚举字段的存储方式（tinyint / varchar / enum 类型）
- 时间戳字段：是否需要 `created_at` / `updated_at`，类型（TIMESTAMP / BIGINT 毫秒）
- 软删除字段：`deleted_at` / `is_deleted`，还是物理删除

---

## 类型四：缓存结构

PRD 极少提及，但实现时必须决策。

**需确认的内容**：
- Key 格式：前缀规范、分隔符、动态部分（如 `user:session:{user_id}`）
- Value 结构：是原始值还是 JSON 对象、若是对象则列出字段
- TTL：过期时间及单位
- 缓存粒度：按用户/按资源/全局

---

## 类型五：消息队列消息体（MQ / Kafka / RabbitMQ 等）

PRD 通常只说"发消息"，省略消息格式。

**需确认的内容**：
- Topic / Queue / Exchange 名称
- 消费组（Consumer Group）名称
- 消息体字段：字段名、类型、是否必填
- 消息 Key（用于分区路由）
- 消息版本字段（若有 schema 演进需求）
- 幂等消费策略（消费者如何判断重复消息）

---

## 类型六：枚举 / 状态值

PRD 常提到字段名但不列出全部合法值。

**需确认的内容**：
- 所有合法枚举值（一个不能少）
- 每个值的中文含义/业务语义
- 对外暴露时的展示文案（若前端需要）
- 非法值的处理方式（报错 / 忽略 / 默认值）

---

## 类型七：配置项（application.yml / .env / 配置中心）

新功能往往引入新配置，PRD 不会列出。

**需确认的内容**：
- 配置键名（与已有配置风格保持一致）
- 类型（string / int / bool / duration...）
- 默认值
- 是否敏感配置（密码/密钥/Token）：需走配置中心加密存储，不可明文提交代码库
- 是否需要支持热更新（不重启生效）
- 各环境（dev/test/prod）的预期值差异

---

## 类型八：文件导入 / 导出格式（CSV / Excel / JSON）

功能说"支持导入"但不说格式细节。

**需确认的内容**：
- 文件格式（CSV / xlsx / JSON Lines...）
- 列定义：列名、顺序、类型、是否必填
- 编码（UTF-8 / GBK）
- 最大行数 / 文件大小限制
- 错误行的处理策略（跳过 / 中止 / 部分成功）

---

## 类型九：Webhook / 事件回调 Payload

接入方需要我方推送时，PRD 通常只说"推送事件"。

**需确认的内容**：
- 触发事件类型列表（枚举）
- 每种事件的 payload 结构（字段名、类型）
- 签名方式（HMAC-SHA256 / 无签名）及签名字段位置（Header / Body）
- 重试策略（最大重试次数、退避间隔）
- 接收方超时阈值

---

## 类型十：搜索索引结构（Elasticsearch / OpenSearch 等）

引入搜索时，字段映射细节 PRD 不会提供。

**需确认的内容**：
- 索引名称及别名策略
- 字段 mapping：字段名、类型（keyword/text/integer/date...）、是否索引
- 分词器（text 类型字段使用哪种 analyzer）
- 是否需要多语言分词
- 写入时机（同步写 / 异步消费 MQ 写）

---

## 使用说明

阶段二提取到以上任一类型的条目时：
1. 对照对应类型的「需确认内容」逐项检查 PRD 是否已说明（判断标准见文件顶部「通用兜底规则」）
2. 任一项 PRD 未说明 → 整个条目标注 `[需确认]`，不拆分为多条
3. 所有 `[需确认]` 条目在阶段三第一批（外部依赖）或第二批（其他）统一向用户确认

若提取到的结构化定义**不属于以上十种类型**，直接适用文件顶部的通用兜底规则。

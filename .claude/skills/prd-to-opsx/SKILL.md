# prd-to-opsx

连接原始PRD与 `openspec-propose` 的精炼层。系统化地从PRD中提取全部细节，注入项目技术上下文，消除所有歧义，再生成高质量的spec制品。

**触发方式**：
```
prd-to-opsx <飞书链接或本地文件路径> [--scope "只实现XXX部分"]
prd-to-opsx  # 无文档，直接用自然语言描述需求
```
范围可用自然语言说明：
> "只做PRD里的支付流程部分" / "只实现第三章" / "先做用户注册，不包括登录"

无文档示例：
> "帮我做手机号+验证码注册功能，需要限流和重复注册校验"

## 执行顺序总览

```
[前置预检]  openspec CLI + skill 可用性检查  ← 最先执行，失败则引导安装/配置后停止
   ↓
阶段零   获取PRD + 确定范围 + 规模判断  ┐
                                        ├─ 可并行执行，两者均完成后进入阶段二
阶段一A  读取项目已有文档（CLAUDE.md/README/specs）┘
   ↓
阶段二   多维度PRD提取 + 歧义质量过滤
   ↓
阶段一B  依赖文件 + 定向代码扫描（用阶段二识别的关键词）← 在阶段二后执行
   ↓                              ← 微需求快速路径：1B与阶段二合并，跳过阶段四
阶段三   歧义识别与分批确认
   ↓
阶段四   富信息PRD摘要（上下文合并）← 微需求跳过
   ↓
阶段五   Spec生成（运行 openspec-propose）
   ↓
阶段六   自检（评估器-优化器循环）
   ↓
阶段七   学习回顾（仅阶段六全部 PASS 时触发）
```

## 执行阶段

### 前置预检：openspec 可用性

同时执行以下两项检查，任一失败则停止，**不进入阶段零**：

1. **CLI 是否安装**：运行 `which openspec`（或 `openspec --version`）
2. **Skill 是否配置**：当前会话可用的 skill 列表中，是否包含 `openspec-propose` 或 `opsx:propose`（两者任一即满足）

有失败时输出对应引导（两项均失败时同时输出两段，各自标注标题）：

- **CLI 未安装**：
  > ⚠️ **[CLI 未安装]** `openspec` CLI 未安装，无法生成 spec 制品。请先完成安装：
  > 1. 参考 openspec 项目 README 获取安装命令并执行
  > 2. 安装后运行 `openspec --version` 确认成功
  > 3. 完成后重新触发 `prd-to-opsx` 继续

- **Skill 未配置**（CLI 已装，但 `openspec-propose` 和 `opsx:propose` 均不在可用 skill 列表中）：
  > ⚠️ **[Skill 未配置]** openspec skill 未配置到当前 Claude 会话，无法调用 spec 生成流程。请选择以下任一方式完成配置：
  > - **方式 A（openspec-propose）**：将 openspec 的 `openspec-propose` skill 文件放入 `.claude/skills/openspec-propose/` 目录
  > - **方式 B（opsx:propose）**：将 openspec 的 `opsx` skill 文件放入 `.claude/skills/opsx/` 目录
  > 配置完成后重启 Claude Code 会话使 skill 生效，再重新触发 `prd-to-opsx`

### 阶段零：获取PRD内容 & 确定范围

**获取内容**（根据输入类型）：
- **飞书链接**（`https://...feishu.cn/...` 或 `https://...larksuite.com/...`）：使用飞书MCP工具读取文档内容
- **本地文件路径**：用 Read 工具读取
- **纯自然语言描述**（无文档）：跳过本步骤，直接进入阶段一A；阶段二以用户描述为提取来源

**确定范围**：
- 若用户指定了 `--scope` 或自然语言说明了只做某部分，读完文档后展示章节结构，确认范围映射：
  > "你要做的「支付流程」对应文档中第4节『订单支付』，是这部分吗？"
- 确认后，**后续所有阶段只处理该范围内的内容**，其余章节忽略
- 若用户未指定范围，直接处理全文，不需要展示章节列表或额外确认

**规模判断（快速路径）**：读完PRD并确定范围后（纯自然语言输入时：用户描述完毕、进入阶段二前），评估规模——若同时满足以下**全部**条件，走**快速路径**：阶段一B与阶段二合并同步执行，跳过阶段四；否则走完整路径：

- 流程数 ≤ 3（「流程数」= PRD中独立的用户操作路径数，即"用户执行X → 系统完成Y"序列各计一个；同一功能的正常流与异常流合计为一个流程）
- 新增实体 ≤ 3
- 涉及的微服务/模块数 ≤ 1（跨服务读写均计入）
- 新增 DB 表 ≤ 1

> 典型误判场景：后台 CRUD 看似是"一个流程"，但若操作跨两个服务或新增两张表，属于完整路径，不走快速路径。

### 阶段一A：读取项目已有文档

**在阅读PRD之前**先完成此步，建立技术约束基线。

按优先级读取：
1. `CLAUDE.md` / `.claude/` 目录 — 项目为AI准备的约定，直接采信
2. `README.md` — 架构说明、技术选型、目录结构
3. `openspec/specs/` 下的 spec.md — 已归档的稳定数据模型和接口定义，**后续直接复用，不重复创建**
4. `openspec/changes/` 下进行中 change 的 design.md — 在途设计决策

记录已明确的内容：技术栈、代码规范、已有实体/接口定义。这些在后续阶段中作为约束直接使用，不再重复提问。

**全新项目（上述文件均不存在）**：向用户确认意图技术栈（语言+框架），记录确认结果后继续。

### 阶段二：多维度PRD提取

必须按维度逐项对照清单提取，禁止自由式摘要总结。

详见 `references/extraction-checklist.md` 五个维度：业务流程 / 数据模型 / 接口契约（含第三方依赖）/ UI交互 / 非功能需求。

提取时：凡是清单条目在PRD中找不到的，标记为「PRD未说明」，这些将成为阶段三的歧义候选。

**长文档分段策略**：若文档章节数 > 10 或正文字符数粗估超过 5 万字，按章节逐节提取，每节完成后以标题标注的代码块暂存结果（如 `## 第3章提取结果`），全部章节处理完再合并，防止中间结果在长上下文中丢失。

**输出格式**：每个维度用 Markdown 二级标题，条目为 bullet 列表，禁止散文段落。使用以下三种标签混排：
```
## 维度一：业务流程
- [提取项] 用户点击「提交」后触发订单创建
- [PRD未说明] 提交失败后是否保留草稿

## 维度三：接口契约
- [需确认] 外游戏信息服务（服务名称已知，接口结构/鉴权/错误码待确认）
```

**歧义质量过滤**：提取完成后，按以下分组分别处理：

**结构化字段强制确认**：对照 `references/structured-fields-checklist.md` 的十种类型，凡属于其中任一类型，逐项核对该类型的「需确认内容」子清单，**任一项 PRD 未说明**即标注 `[需确认]`，直接进入阶段三——无需走下方 (a)(b)(c) 过滤。

**代码扫描不等同于 PRD 说明，不得替代用户确认**：阶段一B 代码扫描中发现的已有实现（字段类型、删除策略、Key 格式、命名规范等），只能在阶段三提问时以「项目已有模式参考」形式附在问题描述里（例如：「项目现有代码使用 time.Time，请确认新表是否沿用？」），不得因此将 `[需确认]` 降格为已处理。结构化字段只有两种方式可以绕过 `[需确认]` 标注：①阶段二时能引用 PRD 原句（此时该条目有PRD依据，无需标注 `[需确认]`）；②阶段三时用户给出显式回答（此时将标签回填为 `[已确认]`）。两者之外，包括代码推断、业务常识以及完全由主对话自行设计的值（接口路径、缓存 Key 格式、TTL、表字段及长度等），**一律视为「PRD未说明」，强制进入阶段三确认，禁止自行填写并标注为已确认**。

**结构化字段规则未覆盖的「PRD未说明」项**，升入阶段三前判断：
- (a) PRD原文有直接表述可引用（须能贴出原句，非"感觉可推断"）？→ 补入并标注 `[引用: 原文"…"]`，不升入阶段三
- (b) 仅影响纯展示文案/按钮文字等UI层表述（该条目不含任何逻辑、约束或后续行为）？→ 补入并标注 `[推断: UI层细节]`，不升入阶段三
- (c) 其余所有情况 → 保留，升入阶段三；判断有疑问时默认走 (c)

**隐含业务逻辑推导**：五个维度提取完成后，基于已提取内容主动推导——凡满足以下任一条件的，标记为 `[推断: 业务逻辑隐含]`，进入阶段三向用户确认：
- 流程A的后置状态变更了实体B的字段，但B的后置条件未显式列出
- 流程C依赖流程D的完成结果，但C的前置条件未引用D
- 状态机中某状态转换必然触发通知/副作用，但异步副作用节未提及
- 两个流程操作同一资源存在并发可能，但幂等/锁策略未说明
- **PRD中存在「共用/合并/不按X维度区分」之类的约束句，该约束隐含 schema 中某个维度字段不应出现**——标注时须指出「该约束意味着 <实体> 不应有 <字段名> 字段，原因：<PRD原句>」

示例：
```
- [推断: 业务逻辑隐含] 用户取消订单（流程C）→ 已扣减的库存应回滚，但维度一后置条件未列出此项
- [推断: 业务逻辑隐含] 支付成功（流程A）和退款（流程D）可能并发操作同一订单状态，幂等策略未说明
```

**阶段二完成性自检与阶段一B合并执行**，见下方阶段一B「合并完成性自检」节。

### 阶段一B：依赖文件 + 定向代码扫描（在阶段二之后执行）

**主体在阶段二完成后**执行，此时已有PRD关键词，代码扫描更有针对性。例外：依赖文件（go.mod等）的读取无需等待阶段二，可与阶段二并行开始；Grep扫描仍须等阶段二识别实体名后执行。（快速路径下与阶段二合并为一步：提取维度时同步执行代码扫描，无需等待提取全部完成。）

- **依赖文件**（阶段一A未覆盖技术栈时补充）：Go: `go.mod` / Java: `pom.xml` / Node: `package.json` / Python: `requirements.txt` 或 `pyproject.toml` / 其他同理
- **定向代码扫描**（始终执行，除非阶段二识别的实体/模块均为全新、代码库中尚不存在——跳过时须显式标注"跳过：代码库无已有代码"）：
  - 用阶段二识别的实体名/模块名 Grep 代码库，找出本次需求将触碰的已有代码
  - Grep 现有 controller/handler/service/repository 模式，确认目录结构和命名规范

若发现新PRD的设计与阶段一A读到的已有 spec/design 有出入，**在阶段三作为歧义提问，不自行裁决**。

输出补充的技术快照（仅补充阶段一A未覆盖的部分）：
```
技术栈: <语言+版本>, <框架>, <主要依赖>（若阶段一A已有则跳过）
API风格: <REST/gRPC/GraphQL等>, <handler层路径>
相关已有代码: <路径>（<说明>）
```

**阶段二 + 阶段一B 合并完成性自检**（快速路径与正常路径均在此执行）：拆分为两个 sub-agent 依次执行，主对话在每步后汇报：

> **Sub-agent prompt 构造规则（所有 sub-agent 均适用）**：传入 Agent 的 prompt 中**只能包含原始数据和核查标准**，禁止包含主对话的分析结论、已识别的问题描述、或任何暗示结果的表述。sub-agent 必须从零开始独立审查——若 prompt 中带入了"问题可能在XXX"之类的提示，等同于污染审查结论。

**Sub-agent【需求提取审计员】**（仅传入：阶段二提取文本，不携带对话上下文）
- 五个维度均有实际提取内容（维度四无UI时须显式标注"跳过：无UI"，而非缺席）
- 对照 `references/structured-fields-checklist.md` 十种类型，凡提取到其中任一类型的条目，均已逐项核对该类型的「需确认内容」子清单，字段不完整的已标注 `[需确认]`，无遗漏
- 隐含逻辑推导已执行（有 `[推断: 业务逻辑隐含]` 条目，或有「隐含逻辑推导：未发现隐含约束」的显式说明）
- 所有 `[推断: 业务逻辑隐含]` 条目已列入阶段三待确认问题列表

→ 主对话汇报：「**提取完整性：PASS / FAIL（<问题列表>）**」。FAIL 时立即补完，重启本 sub-agent 直到 PASS，再进行下一步。

**Sub-agent【代码库扫描员】**（仅传入：Grep 操作记录 + 技术快照，不携带对话上下文）
- 阶段二识别的每个实体名/模块名均已执行 Grep（或已标注"跳过"原因）
- 技术快照已输出（或已显式标注"跳过：阶段一A已有"）

→ 主对话汇报：「**代码扫描：PASS / FAIL（<问题列表>）**」。FAIL 时立即补完，重启本 sub-agent 直到 PASS。

### 阶段三：歧义识别与分批确认

将以下所有待确认项汇总为问题列表：
- **所有维度**的 `[需确认]` 条目（含结构化字段强制确认产生的条目，可能来自任意维度）
- 通过 (a)(b)(c) 过滤后保留的 `[PRD未说明]` 项
- 阶段二隐含逻辑推导产生的 `[推断: 业务逻辑隐含]` 项
- 阶段一B发现的设计冲突

> **纯自然语言输入时**：「PRD未说明」项显著多于有文档场景，确认轮次相应增加，属正常现象。

**规则：不允许任何假设。** 所有不确定项必须确认后才能继续。阶段一A已明确的内容（技术栈、已有鉴权方式等）**不重复提问**。

**P1 及以后优先级的功能**：若阶段二提取到 PRD 标注 P1 或「下期/后续迭代」的功能，必须在第二批问题中显式确认：「PRD 标注 P1 的 <功能名> 是否纳入本次开发范围？」——未确认前不得将其列入任何产出（tasks.md / design.md）。

**提问方式：两批完成，减少用户交互轮次**：

| 批次 | 内容 |
|------|------|
| **第一批** | 所有外部依赖——`references/structured-fields-checklist.md` 类型二（第三方依赖接口）的全部 `[需确认]` 项（优先确认，原因：决定技术方案的根基，影响面最广） |
| **第二批** | 上方问题列表中的其余所有条目 |

若类型二无 `[需确认]` 项，跳过第一批，直接进入第二批。每批提问后等待用户回答，**立即将答案回填到阶段二提取结果中**：将对应条目的标签替换为 `[已确认: <答案摘要>]`；若原标签为 `[PRD未说明]`，则替换为 `[已确认(PRD未说明): <答案摘要>]`（保留来源标记，供阶段七路径A识别）。所有批次完成后，阶段二提取结果中不应再存在未处理的 `[需确认]` 或 `[PRD未说明]` 条目。

**`[已确认]` / `[已确认(PRD未说明)]` 标签的唯一合法来源是用户的明确回答**：每条回填须能一一对应到用户在本阶段的某条具体回答。

**硬性门控**：在所有批次全部确认完毕前（包括「暂用Mock」答复），**禁止进入阶段四**。

**「暂用Mock」路径**（满足门控的特殊情形）：若某外部依赖当前无法确认（对方接口未定、联调未开始），用户可回答「暂用Mock」，这视为有效确认，记录为 `状态=Mock待替换`。后续阶段五生成制品时须为该依赖额外生成：
- `design.md`：定义 Mock 接口（interface/struct），标注 `// MOCK: 替换为真实<服务名>调用`（用 `MOCK:` 而非 `TODO:`，避免触发阶段六的模糊语言扫描）
- `tasks.md`：独立 Mock 桩任务（WHERE=具体文件，WHAT=接口定义，HOW=返回硬编码假数据，AC=调用方编译通过且接口返回预期硬编码响应；不依赖任何外部服务）

**Sub-agent【确认质量审查员】**（仅传入：问题列表 + 回填后的阶段二提取结果，不携带对话上下文）
- 阶段二提取结果中不存在任何 `[需确认]` 或 `[PRD未说明]` 标签（含结构化字段条目）
- 问题列表条目数 = 已回填 `[已确认]` / `[已确认(PRD未说明)]` / `状态=Mock待替换` 条目数，无遗漏
- 所有 `[已确认]` 条目（跳过 `状态=Mock待替换` 条目）的答案摘要不含模糊词（「待定」「随便」「暂定」「视情况」「不确定」「后续确认」等）；含模糊词的标注 `[答案模糊: <条目文本>]`

→ 主对话汇报：「**确认质量：PASS / FAIL（<问题列表>）**」。FAIL 时，将未关闭或答案模糊的条目作为新一批问题向用户补问，回填后重启本 sub-agent，直到 PASS。

### 阶段四：富信息PRD摘要

> **快速路径下跳过本阶段**，直接进入阶段五（以阶段二/三结果为输入）。

在对话上下文中输出一份结构化摘要块（不需要写入文件）。**此摘要块的作用是上下文重置锚**——将阶段一到三散布在对话各处的信息整合为一个干净的近期输入块，避免 openspec-propose 在长上下文中出现检索退化或"上下文焦虑"式的提前收尾。

**摘要长度控制**：摘要本身目标控制在 2000 字以内。若阶段二提取结果过长，提取内容只保留标签行（`[已确认: ...]` / `[已确认(PRD未说明): ...]` / `[推断: 业务逻辑隐含]` 条目），省略 `[引用: ...]` / `[推断: UI层细节]` 行，完整内容仍在对话上下文中可追溯。其中 `[已确认: ...]` 和 `[已确认(PRD未说明): ...]` 标签**必须完整保留**——这是 opsx:propose 区分「PRD提供」和「用户确认补充」的唯一依据。

内容包含：
- 阶段二的多维度提取结果
- 阶段三的所有确认答案（含 `状态=Mock待替换` 的依赖列表）
- 阶段一A/B 的技术快照

**阶段四完成性自检**（快速路径下跳过）：启动一个 sub-agent（仅传入摘要块文本，不携带对话上下文）核查：
- 摘要中有阶段二提取结果（须是实际内容，非"见上文"指针）
- 摘要中有 `状态=Mock待替换` 依赖列表（若有）
- 摘要中有技术快照

→ 主对话汇报：「**摘要完整性：PASS / FAIL（<问题列表>）**」。FAIL 时立即补完，重启 sub-agent 直到 PASS。

### 阶段五：Spec生成

**5.1 生成最小输出清单（调用 openspec-propose 之前完成）**

从**阶段四摘要**（快速路径下：直接使用阶段二提取结果）中的提取内容生成以下三张清单，作为约束随摘要一起传给 openspec-propose。使用阶段四摘要而非原始阶段二文本，可避免长文档场景下回填答案在上下文中被挤远：

```
## 必须在 design.md 中出现的 Schema
- <实体名1>（字段来源：维度二提取项）
- <实体名2>
...

## 必须在 design.md 中出现的 API
- <HTTP方法 路径>（请求/响应结构来源：维度三提取项）
...

## 必须在 tasks.md 中覆盖的场景
- <流程名 · 正常流>（来源：维度一主流程）
- <流程名 · <异常分支描述>>（来源：维度一异常分支）
- <异步副作用名>（来源：维度一异步副作用）
- <推断约束描述>（来源：隐含逻辑推导 `[推断: 业务逻辑隐含]` 已确认项）
...
```

这份清单告诉 openspec-propose "必须输出什么"，而非由它自行决定范围。

**5.2 调用 openspec-propose**

以阶段四摘要（快速路径下：阶段二提取结果）+ 5.1 清单为输入，调用 `openspec-propose`（或 `opsx:propose`）。若存在 `状态=Mock待替换` 项，须同步生成对应的 Mock 接口定义和桩任务（见阶段三「暂用Mock」路径说明）。

### 阶段六：自检

拆分为三个 sub-agent 依次执行，**每个 sub-agent 均以独立审查者视角、默认不合格的立场逐条核查**。每步返回后主对话立即汇报；FAIL 时向用户汇报「⟳ <类型>补全中：<问题列表>，正在<动作>…」，执行补全后重启本 sub-agent，直到 PASS 再启动下一个；连续 FAIL 3 次后暂停，向用户说明剩余问题并请求介入。

**Sub-agent【任务覆盖核查员】**（传入：阶段二完整提取结果 + design.md + tasks.md，不携带对话上下文）
- 维度一每个 `[提取项]` / `[已确认: ...]` / `[已确认(PRD未说明): ...]` / `[推断: 业务逻辑隐含]` 条目（含异常分支、状态机转换、异步副作用）→ tasks.md 是否有对应任务；无则报告「遗漏：<条目文本>」
- 维度二每个实体（含推断项涉及的字段变更）→ design.md 是否有 schema 定义；无则报告「遗漏：<实体名>」
- 维度三每个 API 端点（含推断项涉及的副作用接口）→ design.md 是否有完整请求/响应结构；无则报告「遗漏：<端点>」
- 所有 `[已确认: ...]` / `[已确认(PRD未说明): ...]` 的结构化字段条目（DB表/缓存/MQ消息体/枚举值/Webhook等，来自 `references/structured-fields-checklist.md` 类型三～十；类型一/二已由上方维度三/维度二条目分别覆盖）→ design.md 是否有对应的 schema / 结构定义；无则报告「遗漏：<具体实体/结构名称>」

→ 主对话汇报：「**覆盖率：PASS / FAIL（<遗漏列表>）**」。FAIL 时汇报「⟳ 覆盖率补全中」，直接给出补全内容，重启本 sub-agent。（仅当补全需要用户才知道的业务信息时向用户提问。）

**Sub-agent【制品质量审查员】**（传入：design.md + tasks.md + 技术快照，不携带对话上下文）

`design.md`：
- 每个实体字段有类型+约束——禁止「string类型的ID」、「数字类型」等模糊描述
- 每个API有完整请求/响应结构（非摘要）
- 库/框架选择引用技术快照中的具体项——禁止「使用合适的库」
- 已有实体定义（来自 `openspec/specs/`）以引用方式复用，无重复定义

`tasks.md`（每个任务须满足四要素，缺一即报）：

> WHERE 的路径格式和 HOW/AC 中的技术引用须符合阶段一A/B 技术快照中的实际项目结构，而非照搬下表样本。

| 要素 | 要求 | 反例 | 正例 |
|------|------|------|------|
| **WHERE** | 具体文件/包/函数 | "在后端实现" | `internal/service/order.go: CreateOrder()` |
| **WHAT** | 操作的具体数据结构或接口（引用design.md定义） | "处理订单数据" | `Order结构体（design.md §3.1），写入orders表` |
| **HOW** | 关键实现约束 | （省略） | "通过order_no唯一键保证幂等；与库存扣减在同一事务中" |
| **AC** | 可测试的验收条件 | "功能正常" | "POST /orders 返回201含order_id；重复order_no返回409" |

每组业务实现任务后面须有对应测试任务（四要素同上，WHERE=测试文件，WHAT=覆盖场景含至少一个异常流，HOW=测试类型+框架，AC=通过标准）。

→ 主对话汇报：「**质量核查：PASS / FAIL（<问题列表>）**」。FAIL 时汇报「⟳ 质量补全中」，直接给出符合规范的替代写法，重启本 sub-agent。

**Sub-agent【语言清晰度审查员】**（用 grep 扫描 design.md 和 tasks.md，不需全文重读）

grep：`TBD`、`TODO`、`待定`、`合适的`、`视情况`、`appropriate`、`suitable`、`as needed`、行尾的 `等。` 或 `等，`
- 出现在 `design.md` 或 `tasks.md`：报告位置
- 出现在 `proposal.md`：标记提示即可
- `MOCK:` 标注不触发此规则

→ 主对话汇报：「**模糊语言：PASS / FAIL（<位置列表>）**」。FAIL 时汇报「⟳ 模糊语言补全中」，强制补全，重启本 sub-agent。

**通过条件**：三个 sub-agent 均 PASS——覆盖率全覆盖、design/tasks 质量达标、无模糊语言。三个 sub-agent 全部通过后，自动进入阶段七·学习回顾。

### 阶段七：学习回顾

> **触发条件**：阶段六三个 sub-agent 全部 PASS 后自动触发。阶段六 FAIL 或运行中断时，跳过本阶段。

#### 7.1 Sub-agent 输入

仅传入以下内容，**不携带对话上下文**：

1. 阶段三确认结果：阶段二**完整**（非压缩摘要）提取结果中的全部 `[已确认: ...]` / `[已确认(PRD未说明): ...]` / `[推断: 业务逻辑隐含]` 条目 + 阶段三中用户在回答问题之外主动追加的内容（即：超出所问范围、用户自己引入的新情况）
2. `references/extraction-checklist.md` 全文
3. `references/structured-fields-checklist.md` 全文

#### 7.2 通用性过滤（扫描前先过滤）

候选条目在进入扫描路径之前，**必须通过以下三项通用性检验**，任一不通过即丢弃，不进入候选列表：

1. **业务无关**：该问题对任意业务域（电商、社交、工具、游戏……）均有价值，不依赖本次 PRD 的具体业务场景
2. **技术栈无关**：该问题不预设特定语言（Go/Java/Python）、框架、中间件（BPM、特定 MQ、特定缓存）或团队规范
3. **问题形式**：该条目是「应该向用户确认/检查的问题」，而非「本项目/本功能已决定的答案或规范」

> **反例参照**（这类条目一律不得进入候选）：
> - ❌ `[检查] 用户行为状态表是否需要按 userId+日期/周期维度记录` — 业务场景特定
> - ❌ `[检查] 该功能是否需要 BPM 审批` — 预设了 BPM 集成，技术栈特定
> - ❌ `[需确认] date 字段时区写入规范（Asia/Shanghai 还是 UTC）` — 团队规范，应在项目 CLAUDE.md 中固化，不是通用问题
> - ❌ `[需确认] Go 枚举底层类型与 DB 存储类型的对应关系` — 语言特定
> - ❌ `[检查] 新增端点 URL 前缀是否符合项目路由规范` — 项目规范，不是通用模式
>
> **正例参照**（这类条目可以进入候选）：
> - ✅ `[需确认] 缓存失效策略（TTL / 主动失效 / 不失效）` — 任何引入缓存的项目都需要问
> - ✅ `[检查] 枚举字段是否列出全部合法值及含义` — 任何有枚举的项目都需要问

**丢弃时的处置**：静默丢弃，不进入 7.5 候选列表。若某条目明显适合归档到项目 CLAUDE.md，可在 7.4 输出末尾以一行注明（可选，无强制格式要求）。

#### 7.3 三条扫描路径

扫描时同步过滤已存在项：若候选条目与 checklist 中某条目文本完全相同或语义等价，则标注「已有近似项：<已有条目原文>」并从候选列表中排除，不进入 7.5。

| 路径 | 识别方式 |
|------|---------|
| **A. checklist 空白** | 阶段三确认后标签变为 `[已确认(PRD未说明): <答案>]` 的条目 → 对照 checklist，找无对应项的 |
| **B. 用户主动补充** | 阶段三中用户自己说「还有个情况 / 你漏了 / 还需要考虑」的内容 |
| **C. 结构性空白** | 对比本次提取结果与 checklist 全部维度，发现 checklist 完全没有覆盖的类别 |

#### 7.4 Sub-agent 输出格式

```markdown
## 候选新模式
- [路径A] 建议写入 extraction-checklist.md §维度二·数据模型
  条目文本：`[检查] 枚举字段是否列出全部合法值及含义`
  来源：阶段三确认"status字段取值范围"，checklist 无此项

- [路径B] 建议写入 structured-fields-checklist.md §类型三·缓存
  条目文本：`[需确认] 缓存失效策略（TTL / 主动失效 / 不失效）`
  来源：用户补充"这类需求缓存策略经常没写"
```

若无新模式，输出：`未发现 checklist 未覆盖的新模式。`

→ 主对话汇报：若 sub-agent 返回无新模式，**阶段七静默完成**；否则进入 7.5 展示候选列表。

#### 7.5 用户确认交互

主对话将 sub-agent 返回的候选列表展示给用户，格式如下：

```
阶段七·学习回顾：发现 N 个候选新模式

[1] extraction-checklist.md §维度二
    `[检查] 枚举字段是否列出全部合法值及含义`
    来源：路径A（checklist空白）

[2] structured-fields-checklist.md §类型三·缓存
    `[需确认] 缓存失效策略（TTL / 主动失效 / 不失效）`
    来源：路径B（用户补充）

请确认写入（全部/1,3/不写入）：
```

#### 7.6 写入规则

**写入格式**：追加到对应 checklist 文件指定维度/类型的末尾：

```markdown
<!-- [学习] <运行日期 YYYY-MM-DD> 运行追加 -->
- [检查] 枚举字段是否列出全部合法值及含义
```

**边界规则**：
- 用户回答「不写入」或跳过 → 本次不沉淀，下次运行重新判断
- 写入后输出确认：「已写入 N 条到 extraction-checklist.md，M 条到 structured-fields-checklist.md」
- 阶段七写入失败（文件不可写等） → 警告用户，不报错，本次运行仍视为完成
- 同一次运行最多触发一次阶段七，不重复执行
